# Database upgrades and SHIVA maintenance

SHIVA stores personal records and preferences in Homarr's existing database. Back up that database and wallpaper files together before upgrading; see [the setup guide](../../README.md). Do not use schema push/drop commands against personal data.

## Applying an upgrade

Use the documented `pnpm db:migration:sqlite:run` command (or `pnpm db:migration:postgresql:run` for a deliberately configured PostgreSQL installation). It runs Homarr's migrations, seeds required host data, and calls the existing custom-migration hook, which applies SHIVA's migrations. Production migration binaries use the same sequence.

SHIVA's SQL, snapshots and file journals live in `packages/db/migrations/shiva/{sqlite,postgresql}`. Drizzle records their applied state in `__shiva_migrations` in the same database, using PostgreSQL's `drizzle` schema when applicable. Homarr retains its own unchanged `__drizzle_migrations` history. A future upstream migration numbered `0049` or `0017` therefore does not collide with SHIVA. Both journals are part of a database backup; do not remove either.

Homarr's built-in ZIP export/import transfers the database and its metadata; it does not transfer wallpaper files. A complete SHIVA restore also needs the matching wallpaper directory, preserving its owner subdirectories, and the matching `.env` secrets. Copy those files while stopped as described in [BACKUP.md](BACKUP.md). Restoring only the database retains records and theme references but leaves uploaded images unavailable.

Migrations are append-only after use. Do not rename, renumber, change timestamps, or edit already applied SQL. Add a migration for a new schema change. The foundation's earlier SQL in the host journals was an unpublished, unapplied draft with no durable instance. It was replaced before the first application by the independent SHIVA migration sequence; no populated database history was rewritten.

## Developing schema changes

For upstream-only changes, retain the standard `pnpm db:migration:sqlite:generate` / `pnpm db:migration:postgresql:generate` commands. These use explicit host-only schema exports in `packages/db/schema/upstream`. When updating Homarr, update those exports if upstream adds tables. Runtime schemas and studio still include SHIVA.

For SHIVA changes, update both dialect schemas, then generate each independently from `packages/db`:

```powershell
pnpm with-env drizzle-kit generate --config ./configs/shiva-sqlite.config.ts --name descriptive_change
pnpm with-env drizzle-kit generate --config ./configs/shiva-postgresql.config.ts --name descriptive_change
```

Inspect the generated SQL and both file journals before applying it. Confirm it changes only SHIVA tables and indexes. Keep required upstream user references and cascading lifecycle rules. Test a populated database upgrade and close/reopen before merging a schema change. Never regenerate initial SQL to represent a change after the foundation has been used.

## Verification and limits

The focused `packages/db/test/shiva-migration.spec.ts` check upgrades a populated SQLite host, verifies the host journal is unchanged, writes preferences and exact minor-unit prices, closes/reopens the file, repeats migrations, and applies a later synthetic upstream migration without changing SHIVA records. API tests verify owner isolation and atomic settings revision conflicts.

Both dialect migrations were generated by the pinned Drizzle toolchain. PostgreSQL execution requires a separate configured database and is not certified by the SQLite checks. Windows execution and restoring a personal backup require verification on the intended host.
