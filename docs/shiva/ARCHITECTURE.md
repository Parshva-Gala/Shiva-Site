# Architecture decision

**Base:** Homarr stable `v2.1.2`, commit `473b6cb7c46a147886c41a9b1fabe36d10b6b854`, Apache-2.0. Retain its monorepo, license, and notices. This is a small documented fork of a working application; no admin template or companion backend replaces it.

Source inspection confirmed Mantine/Next.js pages, Auth.js credentials/session handling, authenticated tRPC procedures, Drizzle SQLite/PostgreSQL schemas and migrations, Redis caching, source-defined widgets, and persistent editable dashboard boards. Existing appearance and board customization provide useful infrastructure, but do not implement a complete personal product with native Shopping records and global token-driven appearance controls.

Custom JSX widgets have a restricted validated runtime. They are useful for displaying bounded content, but are not a demonstrated supported route for adding authenticated database tables, arbitrary record CRUD, and application-wide navigation/theme state. SHIVA therefore adds an isolated `/shiva` route, shared validated domain schemas, one authenticated API router, and two tables through Homarr's existing persistence conventions. No second UI framework, database, queue, or service is introduced.

| Responsibility                                      | Implementation                                                                                                                      |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Branding, navigation, Home, Appearance, Shopping UI | `apps/nextjs/src/shiva/` and the `/shiva` route                                                                                     |
| Shared input/theme/layout validation                | `packages/validation/src/shiva.ts`                                                                                                  |
| Authenticated user-scoped operations                | `packages/api/src/router/shiva.ts`                                                                                                  |
| Persistent settings                                 | `shiva_settings`: one settings document per Homarr user                                                                             |
| Native Shopping records                             | `shiva_shopping_record`: user-owned rows with stable IDs                                                                            |
| Schema evolution                                    | `packages/db/migrations/shiva/{sqlite,postgresql}` through the host custom-migration hook; independent journal in the same database |
| Local setup                                         | `scripts/shiva.mjs` and loopback-only `development/shiva.compose.yml`                                                               |

The SHIVA settings document contains the theme, privacy flag, layout, custom presets, and saved layouts. Mutations require an authenticated host user and scope records to that user. Removing the host user cascades to their SHIVA database records; uploaded wallpaper files do not have an account-deletion cleanup hook. Preserve that account and back up before any account deletion. Theme exports contain appearance only and are validated separately from records and secrets.

Native routes retain the common authentication, tRPC, Mantine, localization and notification providers. Homarr's board-modal, Spotlight and assistant providers load together only when entering a host route, preserving their original order. This boundary removes unrelated feature code from native cold loading; actual administration/discard-dialog transitions and focused provider tests protect the retained host behavior. Theme-only consumers use the supported `@homarr/ui/theme` subpath. Native dialogs use immediate transitions and an opaque dimming overlay to give prompt feedback without stacking blur; ordinary wallpaper and panel effects remain configurable.

The native server page authenticates first, then reads settings and the Home-only Shopping summary through the existing protected server API. A supported `@homarr/api/shiva-server` entry reuses the host context, caller and protected router without importing unrelated widget routers. These reads initialize the existing query hooks so useful, correctly themed Home content can render before browser hydration. Reads do not create settings or records, and failed reads retain client retry/error recovery. The date label is calculated once in Asia/Kolkata and shared across the initial render. The host's existing session boundary still invalidates the query tree on identity changes. Home loads its layout editor only on activation; draft state remains with the parent so cancel, save, keyboard reorder and resizing retain their existing behavior.

Global loading and 404 fallbacks use lightweight server-rendered markup. Their former shared Mantine client references resolved to an unrelated board/widget entry in the actual Next.js payload, loading that code on native Home. Host-specific board fallbacks remain intact. Recheck the real cold request graph after upstream bundler or fallback changes; a lazy feature wrapper alone does not prove optional code stays out of the first load.

**Bounded alternatives check:** Dashy `4.7.0` (MIT) provides multi-page YAML and a theme editor, but its inspected persistence centers on dashboard configuration. Homepage `v2.4.0` (GPL-3.0) has server proxies and styling, but its widget authoring guidance favors read-only information cards. Both still need native record storage/API work. Neither presents a concrete maintenance advantage over retaining Homarr's existing authentication, database, and components.

**Visual reference:** Gloation at `98a9bdee8fba83d18261e3f6c2c4763576e4a47f` was inspected through source and screenshots. Wallpaper depth, translucent navigation, subtle highlights, and calm spacing inform SHIVA's original implementation. No license was present, so no CSS, JavaScript, or artwork is copied.

**Limits and risks:** Homarr is larger than a purpose-built personal app and retains Redis and its upstream runtime services. The fork must track changes to Mantine, route providers, auth, API registration, and database schema/migration generation. Existing Homarr administration still exists; SHIVA does not add teams, billing, or collaboration. SHIVA layouts initially support its Home cards and basic preferences; Homarr's board grid is separate. Remote/mobile access and provider credentials are outside this milestone.

Data ownership remains with ClickUp (tasks), calendar providers (appointments), Excel (financial calculations), Obsidian (detailed notes), and message providers (messages). Planned read-only connectors may cache source summaries/references later. SHIVA owns its native records and presentation settings. Notion is optional and no existing information is migrated or modified.
